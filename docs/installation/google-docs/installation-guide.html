Kube-Burner Installation Guide

Product: Kube-Burner v2.6.1  |  Platforms: macOS · Linux · OpenShift 4.x · Kubernetes 1.29+  |  Last validated: April 2026 — tested live on OCP 4.18.20 and OCP 4.21.8

0. Pre-Flight Checklist — Is Kube-Burner Already Installed?

Run these checks first. Before installing anything, spend 30 seconds finding out whether kube-burner is already on the system or already running in the cluster. This saves time and avoids duplicate installs.

Check 1 — Is the binary installed locally?

which kube-burner 2>&1 && kube-burner version 2>&1
OutputWhat it means
A file path + version number✅ Already installed locally — skip Method 1
kube-burner: command not found❌ Not installed locally — follow Method 1 or Method 2 below

Check 2 — Is kube-burner running as a pod in the cluster?

oc get pods -A 2>&1 | grep -i kube-burner
OutputWhat it means
Lines showing pods in Running or Completed state✅ kube-burner has been used in this cluster before
No outputNot currently running (may still have RBAC from a previous install)

Check 3 — Are there completed Jobs from previous runs?

oc get jobs -A 2>&1 | grep -i kube-burner

If you see Complete Jobs, kube-burner has been run successfully on this cluster. View the logs of any past run:

# Replace <namespace> and <job-name> with values from the output above
oc logs job/<job-name> -n <namespace>

Check 4 — Is the RBAC already in place?

oc get serviceaccount kube-burner -A 2>&1
oc get clusterrole kube-burner 2>&1
oc get clusterrolebinding kube-burner 2>&1
OutputWhat it means
All three return names/ages✅ RBAC already set up — skip Step 2 of Method 2
Error from server (NotFound)❌ RBAC not applied — must run Step 2 before benchmarking

Check 5 — Are there existing workload ConfigMaps?

oc get configmap -A 2>&1 | grep -i kube-burner

If ConfigMaps like kube-burner-config or kube-burner-alerts-cfg appear, workload files are already loaded and ready to use.

What to do with the results

SituationAction
Binary + RBAC + ConfigMaps all exist✅ Ready to run a test right now — go to docs/tests/
Binary missing, but RBAC existsRun kube-burner as an in-cluster Job (Method 2) — cluster is already prepared
Nothing existsFollow Method 1 (local binary) or Method 2 (in-cluster Job) below

1. Overview

Kube-Burner is a Kubernetes performance and scale test orchestration tool written in Go. It uses the official client-go library to create, read, patch, and delete cluster resources at configurable rates, collect Prometheus metrics, and measure pod scheduling latency in real time.

There are two ways to install and run kube-burner:

Method Best for Requires local network access to cluster
Local binaryDevelopment, quick tests, vanilla KubernetesYes
In-cluster JobOpenShift, production benchmarks, CI pipelinesNo — runs inside the cluster
Recommendation For OpenShift environments, use the in-cluster Job approach. It is more reliable, avoids firewall restrictions, and reflects how kube-burner is used in production Red Hat performance testing.

3. Method 1 — Local Binary

3.1 macOS

Run the official install script. It detects your architecture (ARM64 or AMD64) automatically:

curl -Ls https://raw.githubusercontent.com/kube-burner/kube-burner/refs/heads/main/hack/install.sh | sh

The binary is installed to ~/.local/bin/kube-burner. Add that directory to your PATH:

echo 'export PATH="$HOME/.local/bin:$PATH"' >> ~/.zshrc
source ~/.zshrc

For bash, replace ~/.zshrc with ~/.bashrc.

3.2 Linux

The same install script works on Linux (x86_64 and ARM64):

curl -Ls https://raw.githubusercontent.com/kube-burner/kube-burner/refs/heads/main/hack/install.sh | sh

To install to a system-wide location, set INSTALL_DIR before running:

INSTALL_DIR=/usr/local/bin \
  curl -Ls https://raw.githubusercontent.com/kube-burner/kube-burner/refs/heads/main/hack/install.sh | sh

Manual Download (optional)

VERSION=v2.6.1
curl -LO "https://github.com/kube-burner/kube-burner/releases/download/${VERSION}/kube-burner-${VERSION}-linux-x86_64.tar.gz"
tar -xzf kube-burner-*.tar.gz
chmod +x kube-burner
mv kube-burner ~/.local/bin/

3.3 Verify the Installation

kube-burner version

Expected output:

Version: v2.6.1
Git commit: 197bd3367ee5bdc6584c21f77c522888b2ad65ac
Build date: 2025-03-01T12:00:00Z
Go version: go1.22.0

Run the built-in cluster health check to confirm connectivity:

kube-burner health-check

Expected output on a healthy cluster:

time="..." level=info msg="Checking for Cluster Health"
time="..." level=info msg="Cluster is healthy."

4. Method 2 — In-Cluster Job (Recommended for OpenShift)

This method runs kube-burner as a Kubernetes Job inside the target cluster using the official container image at quay.io/kube-burner/kube-burner:v2.6.1.

Why in-cluster?

  • No local network path to the API server required.
  • Credentials come from a ServiceAccount — no kubeconfig to manage.
  • The same pattern used by Red Hat performance engineering teams.
  • Works reliably behind firewalls and in CI pipelines.
Step 1 — Create the Benchmark Namespace
# Vanilla Kubernetes
kubectl create namespace burner-test

# OpenShift  (do NOT use the "kube-" prefix — reserved by OCP)
oc new-project burner-test
OpenShift Constraint Project names starting with kube- are reserved for internal system use. Use a different prefix such as burner-, perf-, or bench-.
Step 2 — Apply RBAC

Kube-burner requires a ServiceAccount with a ClusterRole that grants permissions to create and manage resources cluster-wide. Apply the pre-validated RBAC manifest: 

oc apply -f examples/ocp-rbac.yaml

This creates three resources:

ResourceNamePurpose
ServiceAccountkube-burnerIdentity for the in-cluster pod
ClusterRolekube-burnerDefines the allowed API operations
ClusterRoleBindingkube-burnerBinds the role to the ServiceAccount

The ClusterRole grants access to the following resources:

rules:
  - apiGroups: [""]
    resources: [namespaces, pods, services, configmaps, nodes, events]
    verbs: [get, list, watch, create, delete, update, patch]
  - apiGroups: ["apps"]
    resources: [deployments, replicasets, statefulsets, daemonsets]
    verbs: [get, list, watch, create, delete, update, patch]
  - apiGroups: ["batch"]
    resources: [jobs]
    verbs: [get, list, watch, create, delete, update, patch]
Important: events permission The events resource is required for podLatency measurements. Without it, kube-burner logs "events is forbidden" and latency data is incomplete.
Step 3 — Package Your Workload as a ConfigMap

Kube-burner reads its configuration from files. When running in-cluster, these files are delivered via a ConfigMap: 

oc create configmap kube-burner-config \
  --from-file=config.yml=examples/workloads/pod-density-ocp.yml \
  --from-file=pod.yml=examples/workloads/pod-template-ocp.yml \
  -n burner-test

For a node-density workload with Deployment and Service templates:

oc create configmap kube-burner-config \
  --from-file=config.yml=examples/workloads/node-density-ocp.yml \
  --from-file=deployment.yml=examples/workloads/deployment-template-ocp.yml \
  --from-file=service.yml=examples/workloads/service-template-ocp.yml \
  -n burner-test
Step 4 — Apply the Job Manifest
oc apply -f examples/ocp-job.yaml

The Job uses an initContainer to copy the read-only ConfigMap into a writable emptyDir volume before the main container starts. This is necessary because kube-burner writes a log file at startup. 

apiVersion: batch/v1
kind: Job
metadata:
  name: kube-burner-pod-density
  namespace: burner-test
spec:
  backoffLimit: 0
  template:
    spec:
      serviceAccountName: kube-burner
      restartPolicy: Never
      initContainers:
        - name: copy-config
          image: quay.io/kube-burner/kube-burner:v2.6.1
          command: [sh, -c, "cp /config-src/* /config/"]
          volumeMounts:
            - { name: config-src, mountPath: /config-src }
            - { name: workdir,    mountPath: /config }
      containers:
        - name: kube-burner
          image: quay.io/kube-burner/kube-burner:v2.6.1
          workingDir: /config
          command:
            - kube-burner
            - init
            - -c
            - /config/config.yml
            - --uuid=my-benchmark-001
            - --log-level=info
          volumeMounts:
            - { name: workdir, mountPath: /config }
      volumes:
        - name: config-src
          configMap:
            name: kube-burner-config
        - name: workdir
          emptyDir: {}
Step 5 — Monitor the Run

Check Job and pod status:

oc get job kube-burner-pod-density -n burner-test
oc get pods -n burner-test -w

Stream logs in real time:

oc logs -f job/kube-burner-pod-density -n burner-test

A successful run produces output similar to:

time="2026-04-23 14:03:28" level=info  msg="Starting kube-burner (v2.6.1) with UUID my-benchmark-001"
time="2026-04-23 14:03:39" level=info  msg="Pre-load: All images pulled on 3 nodes"
time="2026-04-23 14:03:52" level=info  msg="Triggering job: pod-density"
time="2026-04-23 14:03:56" level=info  msg="pod-density: Ready 99th: 2000 ms   max: 2000 ms"
time="2026-04-23 14:03:56" level=info  msg="pod-density: PodScheduled 99th: 0 ms"
time="2026-04-23 14:04:21" level=info  msg="Finished execution with UUID: my-benchmark-001"

Check the exit code after the Job completes:

oc get pod -l job-name=kube-burner-pod-density -n burner-test \
  -o jsonpath='{.items[0].status.containerStatuses[0].state.terminated.exitCode}'
# 0 = success
# 3 = alert threshold breached
Step 6 — Clean Up
# Delete the Job object
oc delete job kube-burner-pod-density -n burner-test

# Delete the ConfigMap
oc delete configmap kube-burner-config -n burner-test

# Delete all namespaces and resources created by the benchmark
oc delete project burner-test

5. OpenShift-Specific Constraints

Namespace Naming

OpenShift reserves the kube- prefix for internal system projects. Attempting to create a project with this prefix produces the error: 

Error from server (Forbidden): project "kube-burner-test" is forbidden:
cannot request a project starting with "kube-"

Solution: Use any other prefix. Examples: burner-, perf-, bench-, load-.

Single Node OpenShift (SNO) Pod Limit

SNO nodes have a hard limit of 250 pods. Approximately 224 pods are consumed by OpenShift system components, leaving roughly 26 slots for workloads. If a benchmark schedules more pods than available, they remain stuck in Pending with the event "Too many pods".

Before running any benchmark on SNO, calculate available capacity: 
NODE=$(oc get nodes --no-headers -o custom-columns=NAME:.metadata.name | head -1)
LIMIT=$(oc get node $NODE -o jsonpath='{.status.allocatable.pods}')
RUNNING=$(oc get pods -A --no-headers | grep -c Running)
AVAILABLE=$(( LIMIT - RUNNING ))
echo "Available pod slots: $AVAILABLE"

Keep your workload below 80% of the available slots to allow headroom for system churn.

6. Troubleshooting

SymptomRoot CauseResolution
open config.yml: permission denied ConfigMap volume is read-only; kube-burner writes a log file on startup Use the initContainer + emptyDir pattern from Step 4
events is forbidden in pod logs ClusterRole is missing events permission Re-apply examples/ocp-rbac.yaml, which grants events access
cannot request a project starting with "kube-" OCP namespace reservation Rename the namespace; do not use the kube- prefix
Pods stuck in Pending: Too many pods SNO 250-pod node limit reached Calculate free slots (Section 5) and reduce workload size
command not found: kube-burner Binary not on PATH Run export PATH="$HOME/.local/bin:$PATH"
health-check fails: Forbidden Local binary blocked by network policy or firewall Switch to the in-cluster Job approach (Method 2)
Job pod never starts (stuck in Pending) RBAC not applied or ServiceAccount missing Verify: oc get sa kube-burner -n burner-test
