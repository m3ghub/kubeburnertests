Test 18: OCP Node Density — Pods Per Node at Production Scale

> Difficulty: ⭐⭐⭐ Intermediate  
> Time to run: ~10 minutes  
> What it does: Schedules pods per worker node using the exact same benchmark Red Hat runs before shipping every OpenShift release  
> Requires: Multi-node OpenShift cluster

> ⚡ Pre-flight required: Before running this test, verify kube-burner is pullable on your cluster and your environment is ready — see 00-preflight.md (00-preflight.md).

---

What is this test? 🏢

Imagine a skyscraper where every floor is a worker node. You want to know: how many offices (pods) can each floor hold before the elevators (the scheduler) start getting overwhelmed?

The generic pod-density test (Test 02) gives you a rough answer. OCP Node Density gives you the answer that actually matters for OpenShift — because it packs pods the way OpenShift itself does, using the same resource reservations, network policies, and metrics profiles that Red Hat uses internally to validate every OCP release.

When you show this to a customer, you can say: "This is the exact same benchmark Red Hat runs before they ship an OpenShift version. Your cluster passed it."

---

What this test does

node-density is the OpenShift-tuned version of the generic pod-density test.
It schedules a configurable number of pods per worker node using OpenShift-specific
resource definitions — proper tolerations, node selectors, OCP-native network policies —
and collects the full Red Hat performance metrics profile.

Unlike the generic pod-density test, this workload:

- Uses the pre-built metrics profile from kube-burner-ocp (etcd, API server, scheduler, kubelet)
- Applies OCP-specific alert thresholds
- Respects OpenShift's reserved-resources model when sizing pods
- Verifies pods reach Running phase and records latency percentiles (P50/P95/P99)

---

What it measures

| Metric | Description |
|---|---|
| Pod creation latency (P99) | Time from API call to pod scheduled |
| Pod ready latency (P99) | Time from scheduled to container Ready |
| API server request rate | Requests/second during peak creation |
| etcd write throughput | Writes/second to etcd during creation burst |
| kubelet sync latency | Time for kubelet to process each pod |
| Scheduler throughput | Pods scheduled per second |

Step-by-step guide

---

Step 1 — Open the web terminal

Click the >_ icon in the top-right of the console toolbar. Confirm you are logged in:

`bash
oc whoami
oc get nodes --no-headers | awk '{print $1, $2}'
`

All nodes must show Ready.

---

Step 2 — Note how many worker nodes you have

`bash
WORKER_COUNT=$(oc get nodes -l node-role.kubernetes.io/worker --no-headers | wc -l | tr -d ' ')
echo "Worker nodes: $WORKER_COUNT"
`

Choose your pods-per-node target:

| Workers | Starter | Medium | Heavy |
|---|---|---|---|
| 2–3 nodes | 50 pods/node | 100 pods/node | 200 pods/node |
| 4–6 nodes | 100 pods/node | 200 pods/node | 245 pods/node |

---

Step 3 — Create the project and RBAC

`bash
oc new-project burner-node-density
oc create serviceaccount kube-burner -n burner-node-density
`

Apply the ClusterRole and binding:

`bash
oc apply -f - <<'EOF'
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata:
  name: kube-burner
rules:
  - apiGroups: [""]
    resources: [namespaces, pods, services, endpoints, configmaps, secrets, nodes, events, replicationcontrollers, serviceaccounts]
    verbs: [get, list, watch, create, delete, update, patch]
  - apiGroups: [apps]
    resources: [deployments, replicasets, statefulsets, daemonsets]
    verbs: [get, list, watch, create, delete, update, patch]
  - apiGroups: [batch]
    resources: [jobs]
    verbs: [get, list, watch, create, delete, update, patch]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRoleBinding
metadata:
  name: kube-burner
roleRef:
  apiGroup: rbac.authorization.k8s.io
  kind: ClusterRole
  name: kube-burner
subjects:
  - kind: ServiceAccount
    name: kube-burner
    namespace: burner-node-density
EOF
`

Verify:

`bash
oc get serviceaccount kube-burner -n burner-node-density
oc get clusterrole kube-burner
oc get clusterrolebinding kube-burner
`

All three must return a result.

---

Step 4 — Switch to Tab 2

Go to Workloads → Pods in the console. Filter by namespace node-density. Keep this visible — you will see pods appear and transition to Running during the test.

---

Step 5 — Write the config files

Set your parameters (change PODS_PER_NODE to match your choice from Step 2):

`bash
PODS_PER_NODE=50
UUID="node-density-$(date +%s)"
`

Write the config:

`bash
cat > /tmp/node-density-config.yml << EOF
global:
  gc: false
  measurements:
    - name: podLatency
      esIndex: kube-burner

jobs:
  - name: create-pods
    namespace: burner-node-density
    jobType: create
    jobIterations: 1
    namespacedIterations: false
    podWait: true
    waitWhenFinished: true
    maxWaitTimeout: 10m
    objects:
      - objectTemplate: /config/pod-template.yml
        replicas: ${PODS_PER_NODE}

  - name: delete-pods
    namespace: burner-node-density
    jobType: delete
    waitForDeletion: true
    objects:
      - apiVersion: v1
        kind: Pod
        labelSelector: {kube-burner-job: create-pods}
EOF
`

Write the pod template:

`bash
cat > /tmp/pod-template.yml << 'EOF'
apiVersion: v1
kind: Pod
metadata:
  name: density-pod-{{.Iteration}}-{{.Replica}}
  labels:
    app: density
    kube-burner-job: create-pods
spec:
  containers:
    - name: pause
      image: gcr.io/google_containers/pause:3.1
      resources:
        requests:
          cpu: 10m
          memory: 10Mi
EOF
`

---

Step 6 — Create the ConfigMap

`bash
oc create configmap node-density-config \
  --from-file=config.yml=/tmp/node-density-config.yml \
  --from-file=pod-template.yml=/tmp/pod-template.yml \
  -n burner-node-density
`

Verify:

`bash
oc get configmap node-density-config -n burner-node-density
`

---

Step 7 — Launch the Job

`bash
cat << JOBYAML | oc apply -f -
apiVersion: batch/v1
kind: Job
metadata:
  name: kb-node-density
  namespace: burner-node-density
spec:
  backoffLimit: 0
  template:
    spec:
      serviceAccountName: kube-burner
      restartPolicy: Never
      initContainers:
        - name: copy-config
          image: quay.io/kube-burner/kube-burner:v2.7.3
          command: [sh, -c, "cp /config-src/* /config/"]
          volumeMounts:
            - {name: config-src, mountPath: /config-src}
            - {name: workdir,    mountPath: /config}
      containers:
        - name: kube-burner
          image: quay.io/kube-burner/kube-burner:v2.7.3
          workingDir: /config
          command: [kube-burner, init, -c, /config/config.yml, --uuid=${UUID}]
          volumeMounts:
            - {name: workdir, mountPath: /config}
      volumes:
        - name: config-src
          configMap:
            name: node-density-config
        - name: workdir
          emptyDir: {}
JOBYAML
`

---

Step 8 — Wait for the pod to start

`bash
oc get pod -n burner-node-density -w
`

Wait for Running (init container copies config first — takes ~10 seconds). Then stream logs:

`bash
oc logs -f job/kb-node-density -n burner-node-density
`

---

Step 9 — Watch the cluster while it runs

Tab 2 (Workloads → Pods): Watch pods appear and turn green.

Tab 3 (Observe → Metrics): Paste this query:
`
sum(kube_pod_status_phase{phase="Running"})
`
Watch the number climb.

Tab 4 (Compute → Nodes): Click any worker node — watch CPU spike as it handles the pod creation surge.

What to say to a customer: "Watch that number climb — each unit is a pod that just became Ready. We started 50 at once and the cluster handled every single one."

---

Step 10 — Read the results

When the job completes, the final log lines show:

`
INFO podLatency:
INFO   P50:  2.3s
INFO   P95:  5.1s
INFO   P99:  8.4s    ← > 15s may indicate scheduler or etcd bottleneck
INFO   Max: 12.1s
INFO Finished execution. UUID: node-density-...
`

---

Step 11 — Clean up

`bash
oc delete job kb-node-density -n burner-node-density 2>/dev/null || true
oc delete configmap node-density-config -n burner-node-density 2>/dev/null || true
oc delete project burner-node-density
oc delete clusterrole kube-burner 2>/dev/null || true
oc delete clusterrolebinding kube-burner 2>/dev/null || true
`

Verify clean:

`bash
oc get projects | grep burner-node-density
Should return nothing
`

---

Expected results

| Cluster type | Expected P99 pod-ready latency | Max API server rate |
|---|---|---|
| 3-node SNO-adjacent | 5–15 s | ~200 req/s |
| Standard 3-worker OCP | 2–8 s | ~400 req/s |
| Large OCP (10+ workers) | 2–6 s | ~800 req/s |

> Values depend heavily on etcd disk speed and API server replica count.

A P99 over 15 seconds typically means:
- etcd disk I/O is saturated
- API server is rate-limiting
- Worker nodes have insufficient CPU for kubelet to process the surge

---

Troubleshooting

| Problem | Fix |
|---|---|
| serviceaccount "kube-burner" not found | Re-run Step 3 — create the SA as a separate command |
| Pods stuck in Pending: Too many pods | Node has hit pod limit — reduce PODS_PER_NODE |
| ImagePullBackOff on kube-burner | quay.io unreachable — check cluster pull secrets |
| Job pod never starts | Check: oc describe job kb-node-density -n burner-node-density | grep Events |
| P99 > 30s | Reduce PODS_PER_NODE — you found the ceiling |
