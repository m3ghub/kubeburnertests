Test 07: Patch Workload — The Update Test

> Difficulty: ⭐⭐ Intermediate  
> Time to run: ~8 minutes  
> What it does: Updates (patches) existing Kubernetes resources at speed to measure how the cluster handles rolling updates and label changes

> ⚡ Pre-flight required: Before running this test, verify kube-burner is pullable on your cluster and your environment is ready — see 00-preflight.md (00-preflight.md).

---

What is this test? ✏️

Imagine you have 100 sticky notes on a whiteboard and you need to change the colour sticker on every single one — as fast as possible.

The Patch workload does this to your Kubernetes objects. It:
1. Takes existing Deployments or Pods that kube-burner created
2. Sends PATCH requests to update them (labels, annotations, replica counts, etc.)
3. Measures how fast the API server and controllers apply each change

This test is important because real clusters constantly patch objects — rolling deployments, label updates, resource scaling — and you want to know how fast your cluster can keep up.

---

What does it measure?

| Metric | What it means |
|---|---|
| API server write latency | How fast patch requests complete |
| Controller reconciliation time | How fast the Deployment controller notices and applies the change |
| etcd write latency | How fast the cluster database saves the updated objects |

---

How it works

`
Step 1 (create):   Deployment-1 ──► replicas: 1, label: version=v1
                   Deployment-2 ──► replicas: 1, label: version=v1
                   Deployment-3 ──► replicas: 1, label: version=v1

Step 2 (patch):    PATCH Deployment-1 ──► label: version=v2
                   PATCH Deployment-2 ──► label: version=v2
                   PATCH Deployment-3 ──► label: version=v2
                          ↑
                     All done at once, high QPS

Step 3 (measure):  How long did each patch take?
                   Did controllers respond correctly?
`

Before you start ✅

- [ ] kube-burner installed
- [ ] Logged in as cluster-admin
- [ ] RBAC applied
- [ ] ~8 minutes available

Step-by-step guide

Step 1 — Create the namespace

> Do this first — every other step depends on it.

`bash
oc new-project burner-patch-test
`

You should see:
`
Now using project "burner-patch-test" on server "https://api.<your-cluster>:6443"
`

> OpenShift only: Never use kube- at the start of the name — it is reserved by the system and will be rejected.

Step 2 — Set up RBAC

Every test needs a ServiceAccount, ClusterRole, and ClusterRoleBinding. Run all three commands — they are safe to re-run if any already exist.

2a — Create the ServiceAccount in this namespace:

`bash
oc create serviceaccount kube-burner -n burner-patch-test \
  --dry-run=client -o yaml | oc apply -f -
`

2b — Apply the ClusterRole and ClusterRoleBinding (once per cluster):

> These are applied inline below — no local file needed. Safe to re-run at any time.

`bash
oc apply -f - <<'EOF'
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata:
  name: kube-burner
rules:
  - apiGroups: [""]
    resources: [namespaces, pods, services, endpoints, configmaps, secrets, nodes, events, replicationcontrollers, serviceaccounts]
    verbs: [get, list, watch, create, delete, update, patch]
  - apiGroups: [apps]
    resources: [deployments, replicasets, statefulsets, daemonsets]
    verbs: [get, list, watch, create, delete, update, patch]
  - apiGroups: [batch]
    resources: [jobs]
    verbs: [get, list, watch, create, delete, update, patch]
  - apiGroups: [networking.k8s.io]
    resources: [networkpolicies, ingresses]
    verbs: [get, list, watch, create, delete, update, patch]
  - apiGroups: [kubevirt.io]
    resources: [virtualmachines, virtualmachineinstances]
    verbs: [get, list, watch, create, delete, update, patch]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRoleBinding
metadata:
  name: kube-burner
roleRef:
  apiGroup: rbac.authorization.k8s.io
  kind: ClusterRole
  name: kube-burner
subjects:
  - kind: ServiceAccount
    name: kube-burner
    namespace: burner-patch-test
EOF
`

2c — Add this namespace to the ClusterRoleBinding:

`bash
oc patch clusterrolebinding kube-burner \
  --type=json \
  -p='[{"op":"add","path":"/subjects/-","value":{"kind":"ServiceAccount","name":"kube-burner","namespace":"burner-patch-test"}}]' 2>/dev/null || true
`

> The || true at the end means this command will not fail if the namespace is already listed. It is safe to run every time.

Verify all three are in place before continuing:

`bash
oc get serviceaccount kube-burner -n burner-patch-test
oc get clusterrole kube-burner
oc get clusterrolebinding kube-burner -o jsonpath='{.subjects[*].namespace}'
`

The last command should include burner-patch-test in the output.

Step 3 — Create config files

This test runs in two phases — first create, then patch.

Create patch-config.yml:

`bash
cat > /tmp/patch-config.yml << 'EOF'
global:
  gc: true
  measurements:
    - name: podLatency

jobs:
  # Phase 1: Create the resources
  - name: patch-setup
    namespace: burner-patch-test
    jobType: create
    jobIterations: 1
    qps: 20
    burst: 20
    objects:
      - objectTemplate: deployment.yml
        replicas: 10
    waitWhenFinished: true
    podWait: true
    maxWaitTimeout: 5m

  # Phase 2: Patch the resources
  - name: patch-workload
    namespace: burner-patch-test
    jobType: patch
    jobIterations: 1
    qps: 20
    burst: 20
    objects:
      - kind: Deployment
        apiVersion: apps/v1
        labelSelector:
          app: kube-burner
        patchType: merge
        objectTemplate: patch.json
EOF
`

Create deployment.yml:

`bash
cat > /tmp/deployment.yml << 'EOF'
apiVersion: apps/v1
kind: Deployment
metadata:
  name: burner-dep-{{.Iteration}}-{{.Replica}}
  labels:
    app: kube-burner
    version: v1
spec:
  replicas: 1
  selector:
    matchLabels:
      app: burner-dep-{{.Iteration}}-{{.Replica}}
  template:
    metadata:
      labels:
        app: burner-dep-{{.Iteration}}-{{.Replica}}
        version: v1
    spec:
      containers:
        - name: app
          image: registry.k8s.io/pause:3.9
          resources:
            requests:
              cpu: 1m
              memory: 10Mi
EOF
`

Create patch.json (the change to apply — this bumps the label from v1 to v2):

`bash
cat > /tmp/patch.json << 'EOF'
{
  "metadata": {
    "labels": {
      "version": "v2",
      "patched-by": "kube-burner"
    }
  }
}
EOF
`

---

Step 4 — Package into a ConfigMap

`bash
oc create configmap patch-config \
  --from-file=config.yml=/tmp/patch-config.yml \
  --from-file=deployment.yml=/tmp/deployment.yml \
  --from-file=patch.json=/tmp/patch.json \
  -n burner-patch-test
`

---

Step 5 — Run the test!

`bash
cat <<'EOF' | oc apply -f -
apiVersion: batch/v1
kind: Job
metadata:
  name: kb-patch
  namespace: burner-patch-test
spec:
  backoffLimit: 0
  template:
    spec:
      serviceAccountName: kube-burner
      restartPolicy: Never
      initContainers:
        - name: copy-config
          image: quay.io/kube-burner/kube-burner:v2.6.1
          command: [sh, -c, "cp /config-src/* /config/"]
          volumeMounts:
            - {name: config-src, mountPath: /config-src}
            - {name: workdir,    mountPath: /config}
      containers:
        - name: kube-burner
          image: quay.io/kube-burner/kube-burner:v2.6.1
          workingDir: /config
          command: [kube-burner, init, -c, /config/config.yml, --uuid=patch-001]
          volumeMounts:
            - {name: workdir, mountPath: /config}
      volumes:
        - name: config-src
          configMap:
            name: patch-config
        - name: workdir
          emptyDir: {}
EOF
`

---

Step 6 — Watch the labels change

While the test is running, watch the Deployments get their labels updated:

`bash
oc get deployments -n burner-patch-test \
  -o custom-columns="NAME:.metadata.name,VERSION:.metadata.labels.version" -w
`

You will see v1 → v2 as the patch is applied to each Deployment.

---

Step 7 — Stream logs and read results

`bash
oc logs -f job/kb-patch -n burner-patch-test
`

Expected output:

`
time="..." level=info msg="Triggering job: patch-setup (create)"
time="..." level=info msg="patch-setup: 10/10 pods ready"
time="..." level=info msg="Triggering job: patch-workload (patch)"
time="..." level=info msg="Patching 10 Deployments in burner-patch-test"
time="..." level=info msg="patch-workload: 10 patches applied in 450ms"
time="..." level=info msg="Finished execution. UUID: patch-001"
`

Good patch latency:
- Under 500ms for 10 objects on a healthy API server

---

Step 8 — Verify the patches were applied

`bash
oc get deployments -n burner-patch-test \
  -o custom-columns="NAME:.metadata.name,VERSION:.metadata.labels.version"
`

All Deployments should show v2 in the VERSION column.

---

Step 9 — Clean up

`bash
oc delete job kb-patch -n burner-patch-test
oc delete configmap patch-config -n burner-patch-test
oc delete project burner-patch-test
`

---

Troubleshooting

| Problem | Fix |
|---|---|
| no objects found to patch | The create phase didn't complete; check setup job logs |
| Patches applied but pods restarted | Normal if you patch the pod template — Deployments roll out |
| Very slow patch times | API server is under load; reduce qps |
