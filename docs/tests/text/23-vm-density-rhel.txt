Test 23: RHEL 9 VM Fleet Density — Enterprise Linux at Scale

> Difficulty: ⭐⭐⭐⭐ Advanced  
> Time to run: ~20–40 minutes  
> What it does: Creates N RHEL 9 virtual machines simultaneously and measures KubeVirt boot latency for enterprise Linux workloads  
> Requires: OpenShift Virtualization 4.x, multi-node cluster, RHEL 9 golden image available  
> VM Image: RHEL 9 golden image from openshift-virtualization-os-images (pre-loaded on most OCP Virt clusters)

---

What is this test? 🐧

CirrOS boots in 5 seconds. Your customers are not running CirrOS. They are running RHEL — the same operating system that runs their databases, their middleware, their compliance-critical workloads.

This test uses the RHEL 9 golden image that OpenShift Virtualization pre-loads on the cluster and asks: how many enterprise Linux VMs can OpenShift Virtualization boot at the same time?

When you show this to a customer migrating from VMware: "Every VM you see booting is RHEL 9 — the same OS running your production workloads right now. We're starting them all simultaneously. This is what your migration day looks like."

What makes RHEL different from CirrOS:
- Boots the full Linux kernel + systemd + cloud-init (~90 seconds vs 5 seconds)
- Uses cloud-init for user injection (realistic provisioning workflow)
- Needs 2 GiB RAM per VM (vs 512 MiB for CirrOS)
- Represents actual customer database, app server, and middleware workloads

---

What it measures

| Metric | Description | RHEL vs CirrOS |
|---|---|---|
| VMI ready latency P50/P95/P99 | Time from VM creation to Running phase | 60–120 s vs 10–30 s |
| virt-controller queue depth | How many VMs awaiting reconciliation | Higher with slower-booting VMs |
| Node memory pressure | RAM consumed during concurrent boot | 2 Gi per VM vs 512 Mi |
| cloud-init completion | Time for initial user configuration | ~30 s extra vs none |
| virt-handler load | Reconcile loop load during QEMU startup | Higher sustained load |

Pre-flight checklist

Run all of these before starting. Every check must pass.

Check 1 — Logged in and cluster is reachable

`bash
oc whoami
oc get nodes --no-headers | awk '{print $1, $2}'
`

Expected: your username, and each node showing Ready.

---

Check 2 — OpenShift Virtualization is installed

`bash
oc get hyperconverged -A
`

Expected: a row showing PHASE: Deployed. If empty — VM tests are not available on this cluster.

---

Check 3 — kube-burner image is pullable (required by every test)

`bash
Delete any leftover test pod
oc delete pod kb-preflight -n default 2>/dev/null || true

Create the test pod
oc run kb-preflight \
  -n default \
  --image=quay.io/kube-burner/kube-burner:v2.6.1 \
  --restart=Never \
  --command -- kube-burner version
`

Run this every 15 seconds until STATUS shows Completed:

`bash
oc get pod kb-preflight -n default
`

Then read the output:

`bash
oc logs kb-preflight -n default | grep -i version
Expected: Version: v2.6.1
`

Clean up:

`bash
oc delete pod kb-preflight -n default 2>/dev/null || true
`

| STATUS | Meaning |
|---|---|
| Completed | kube-burner image pullable — all tests will work |
| ImagePullBackOff | quay.io/kube-burner is blocked — no tests can run until this is resolved |
| Pending / ContainerCreating | Still pulling — wait 60 s and recheck |

Check 4 — RHEL image source (pick the method that works on your cluster)

Run the auto-detect script from 00-preflight.md (00-preflight.md) to find out which method is available, or check manually:

`bash
Method A check — OCP golden image (recommended)
oc get datasource rhel9 -n openshift-virtualization-os-images 2>/dev/null || \
  oc get datasource rhel8 -n openshift-virtualization-os-images 2>/dev/null || \
  echo "No RHEL DataSource found — try Method B or C"

Method B check — quay.io/containerdisks (external registry)
oc delete pod rhel-method-b -n default 2>/dev/null || true
oc run rhel-method-b -n default \
  --image=quay.io/containerdisks/rhel9:9.0 --restart=Never --command -- true
Watch: oc get pod rhel-method-b -n default (Completed=works, ImagePullBackOff=blocked)
Cleanup: oc delete pod rhel-method-b -n default 2>/dev/null || true

Method C check — HTTP QCOW2 (free RHEL-compatible, no registry needed)
curl -s --connect-timeout 10 \
  "https://repo.almalinux.org/almalinux/9/cloud/x86_64/images/" \
  -o /dev/null -w "HTTP egress: %{http_code}\n"
200 = Method C works
`

| Method | Works when | VM image |
|---|---|---|
| A — OCP golden image | OpenShift Virtualization golden images enabled | RHEL 9 (official Red Hat) |
| B — quay.io/containerdisks | External registry reachable | RHEL 9 containerDisk |
| C — QCOW2 via HTTP | HTTP egress available, no registry needed | AlmaLinux/Rocky/CentOS (free, 1:1 RHEL-compatible) |

See 00-preflight.md (00-preflight.md) for full method details and VM template for each method.

Step 7 — Write the RHEL 9 VM template

Choose the template that matches the method you confirmed in Check 4 of pre-flight.

---

Method A — OCP golden image (recommended)

Uses the RHEL 9 DataSource already on the cluster. No external registry needed:

`bash
cat > /tmp/rhel-vm-template.yml << 'EOF'
apiVersion: kubevirt.io/v1
kind: VirtualMachine
metadata:
  name: rhel-vm-{{.Iteration}}-{{.Replica}}
  labels:
    app: rhel-fleet
    os: rhel9
    kube-burner-job: create-rhel-vms
spec:
  running: true
  dataVolumeTemplates:
    - metadata:
        name: rhel-disk-{{.Iteration}}-{{.Replica}}
      spec:
        sourceRef:
          kind: DataSource
          name: rhel9                                   # Change to rhel8 if needed
          namespace: openshift-virtualization-os-images
        storage:
          resources:
            requests:
              storage: 30Gi
  template:
    metadata:
      labels:
        app: rhel-fleet
        os: rhel9
    spec:
      domain:
        cpu:
          cores: 1
        resources:
          requests:
            memory: 2Gi
        devices:
          disks:
            - name: rootdisk
              disk:
                bus: virtio
            - name: cloudinitdisk
              disk:
                bus: virtio
          interfaces:
            - name: default
              masquerade: {}
      networks:
        - name: default
          pod: {}
      volumes:
        - name: rootdisk
          dataVolume:
            name: rhel-disk-{{.Iteration}}-{{.Replica}}
        - name: cloudinitdisk
          cloudInitNoCloud:
            userData: |
              #cloud-config
              hostname: rhel-vm-{{.Iteration}}-{{.Replica}}
              user: cloud-user
              password: redhat123
              chpasswd:
                expire: false
              ssh_pwauth: true
EOF
`

Method B — quay.io/containerdisks (external registry)

Use when Method A is not available but quay.io/containerdisks is reachable. No storage PVC needed — image loads as a memory-mapped containerDisk:

`bash
cat > /tmp/rhel-vm-template.yml << 'EOF'
apiVersion: kubevirt.io/v1
kind: VirtualMachine
metadata:
  name: rhel-vm-{{.Iteration}}-{{.Replica}}
  labels:
    app: rhel-fleet
    os: rhel9
    kube-burner-job: create-rhel-vms
spec:
  running: true
  template:
    metadata:
      labels:
        app: rhel-fleet
        os: rhel9
    spec:
      domain:
        cpu:
          cores: 1
        resources:
          requests:
            memory: 2Gi
        devices:
          disks:
            - name: rootdisk
              disk:
                bus: virtio
            - name: cloudinitdisk
              disk:
                bus: virtio
          interfaces:
            - name: default
              masquerade: {}
      networks:
        - name: default
          pod: {}
      volumes:
        - name: rootdisk
          containerDisk:
            image: quay.io/containerdisks/rhel9:9.0
        - name: cloudinitdisk
          cloudInitNoCloud:
            userData: |
              #cloud-config
              hostname: rhel-vm-{{.Iteration}}-{{.Replica}}
              user: cloud-user
              password: redhat123
              chpasswd:
                expire: false
              ssh_pwauth: true
EOF
`

> Note: If using Method B, remove cdi.kubevirt.io from the ClusterRole in Step 3 (no DataVolumes needed).

  backoffLimit: 0

          command: [kube-burner, init, -c, /config/config.yml, --uuid=${UUID}]

            name: rhel-fleet-config

Troubleshooting

| Problem | Fix |
|---|---|
| datasource "rhel9" not found (Method A) | Run oc get datasource -n openshift-virtualization-os-images to see available RHEL versions. Use rhel8 if rhel9 is absent. |
| ImagePullBackOff on RHEL image (Method B) | quay.io/containerdisks/rhel9:9.0 blocked — switch to Method A or C |
| DataVolume stuck in ImportScheduled (Method C) | HTTP egress blocked — check oc describe datavolume -n burner-rhel-fleet for network error |
| DataVolume import taking > 30 min (Method C) | QCOW2 download is slow (file is 600 MB – 2 GB) — wait or try a closer mirror |
| VMs stuck in Provisioning > 10 min | CDI is cloning — check oc get datavolume -n burner-rhel-fleet for status |
| cannot create resource "datavolumes" | ClusterRole missing cdi.kubevirt.io — re-apply Step 3 RBAC (not needed for Method B) |
| VMs stuck in Scheduling | Not enough RAM — reduce VM_COUNT (each VM needs 2 Gi) |
| serviceaccount "kube-burner" not found | Re-run Step 3 — create SA before applying ClusterRoleBinding |
| virt-launcher pods OOMKilled | Worker node out of memory — reduce VM_COUNT |
| P99 > 5 minutes | QEMU startup bottleneck — check oc adm top nodes for pressure |
| ImagePullBackOff on kube-burner job pod | Run pre-flight Check 1 — quay.io/kube-burner must be reachable |
