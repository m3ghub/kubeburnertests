Test 24: Windows Server VM Fleet Density — VMware Migration Demo

> Difficulty: ⭐⭐⭐⭐ Advanced  
> Time to run: 30–60 minutes  
> What it does: Creates N Windows Server 2022 VMs simultaneously and measures boot latency — the most compelling VMware migration demo you can run  
> Requires: OpenShift Virtualization 4.x, multi-node cluster, Windows golden image pre-imported  
> VM Image: win2k22 DataVolume from openshift-virtualization-os-images (or customer-provided)

---

What is this test? 🪟

When a customer is evaluating whether to move their VMware estate to OpenShift, the most common objection is:  
"But can it run our Windows workloads?"

This test answers that with a live demonstration: N Windows Server 2022 VMs booting simultaneously on OpenShift Virtualization.

Windows takes 3–8 minutes to boot (vs 5 seconds for CirrOS). That is not a problem — it is realistic. Showing a customer 10 Windows VMs come online one-by-one over 5 minutes, each one in the OpenShift console VM list, is more powerful than any slide.

What to say: "These are Windows Server 2022 instances — the same OS running your SQL Server, your IIS, your Active Directory. Watch them boot. We started all of them at the same time and the cluster handled it without breaking a sweat."

---

Pre-flight — Windows image setup

Windows VMs require a pre-imported disk image. OpenShift Virtualization provides this through its golden images feature. Check if the Windows image already exists:

`bash
Check for the Windows Server 2022 golden image
oc get datavolume win2k22 -n openshift-virtualization-os-images 2>/dev/null || \
  echo "Windows golden image not found"

Also check for the DataSource (alternative source)
oc get datasource win2k22 -n openshift-virtualization-os-images 2>/dev/null || \
  echo "Windows DataSource not found"
`

If the golden image exists — you are ready

The golden image exists if oc get datavolume win2k22 -n openshift-virtualization-os-images returns a result. Skip to Step 1.

If the golden image does NOT exist — import it

OpenShift Virtualization can import the Windows image using the CDI (Containerized Data Importer). This requires a Windows Server 2022 ISO available via HTTP. Ask your cluster administrator, or enable the OpenShift Virtualization operator's automatic image downloads:

`bash
Option 1: Enable automatic Windows image download via the operator
oc patch hco kubevirt-hyperconverged \
  -n openshift-cnv \
  --type merge \
  -p '{"spec":{"featureGates":{"deployKubevirtIpamController":true}}}'

Option 2: Check if a boot source exists that can be used
oc get datasource -n openshift-virtualization-os-images | grep win
`

If no Windows image is available on the cluster, contact your cluster administrator to import one before running this test. The test will fail without a valid Windows disk source.

---

What it measures

| Metric | Description | Windows vs CirrOS |
|---|---|---|
| VMI ready latency P50/P95/P99 | Time from VM creation to Running | 3–8 min vs 5–15 s |
| DataVolume clone time | Time to clone the Windows image per VM | 30–120 s per VM |
| virt-handler load | Sustained reconcile during long Windows boot | Higher sustained load |
| Node memory pressure | 4 Gi RAM per VM | 4 Gi per VM vs 512 Mi |
| Storage I/O | Disk write throughput during Windows boot | Very high — Windows writes a lot |

Pre-flight checklist

Run all checks before starting. Every check must pass.

Check 1 — kube-burner image is pullable

`bash
oc delete pod kb-preflight -n default 2>/dev/null || true
oc run kb-preflight \
  -n default \
  --image=quay.io/kube-burner/kube-burner:v2.7.3 \
  --restart=Never \
  --command -- kube-burner version
`

Run every 15 seconds until Completed:

`bash
oc get pod kb-preflight -n default
oc logs kb-preflight -n default | grep -i version   # Expected: Version: v2.7.3
oc delete pod kb-preflight -n default 2>/dev/null || true
`

If ImagePullBackOff — quay.io is blocked on this cluster. No tests can run until resolved.

Check 2 — Windows golden image is available

`bash
Must show PHASE: Succeeded
oc get datavolume win2k22 -n openshift-virtualization-os-images
`

If not found — see the Pre-flight — Windows image setup (#pre-flight--windows-image-setup) section below.

Check 3 — Storage class available for DataVolume cloning

`bash
oc get storageclass
`

Note the default storage class name. You may need to set storageClassName in the VM template if it is not auto-selected.

Check 4 — Memory available

`bash
oc adm top nodes
`

Each Windows VM needs 4 GiB + 50 Gi storage. For 4 VMs: need ~16 GiB RAM and ~200 GiB storage free.

Step 2 — Choose how many Windows VMs to create

| Cluster size | Workers | Available RAM | Starter | Medium | Heavy |
|---|---|---|---|---|---|
| Small | 2–3 | 32–64 Gi per node | 2 VMs | 4 VMs | 6 VMs |
| Medium | 4–6 | 64+ Gi per node | 4 VMs | 8 VMs | 12 VMs |
| Large | 6+ | 128+ Gi per node | 6 VMs | 12 VMs | 20 VMs |

> Windows uses significantly more RAM and storage than RHEL or CirrOS. Start conservatively.

Step 4 — Switch to Tab 2

Step 6 — Write the config file

`bash
cat > /tmp/windows-fleet-config.yml << EOF
global:
  gc: false
  measurements:
    - name: vmiLatency

jobs:
  - name: create-windows-vms
    namespace: burner-windows-fleet
    jobType: create
    jobIterations: 1
    namespacedIterations: false
    podWait: false
    waitWhenFinished: true
    maxWaitTimeout: 60m
    objects:
      - objectTemplate: /config/windows-vm-template.yml
        replicas: ${VM_COUNT}

  - name: delete-windows-vms
    namespace: burner-windows-fleet
    jobType: delete
    waitForDeletion: true
    objects:
      - apiVersion: kubevirt.io/v1
        kind: VirtualMachine
        labelSelector: {kube-burner-job: create-windows-vms}
EOF
`

        resources:

            relaxed: {}

Step 9 — Launch the Job

`bash
cat << JOBYAML | oc apply -f -
apiVersion: batch/v1
kind: Job
metadata:
  name: kb-windows-fleet
  namespace: burner-windows-fleet
spec:
  backoffLimit: 0
  template:
    spec:
      serviceAccountName: kube-burner
      restartPolicy: Never
      initContainers:
        - name: copy-config
          image: quay.io/kube-burner/kube-burner:v2.7.3
          command: [sh, -c, "cp /config-src/* /config/"]
          volumeMounts:
            - {name: config-src, mountPath: /config-src}
            - {name: workdir,    mountPath: /config}
      containers:
        - name: kube-burner
          image: quay.io/kube-burner/kube-burner:v2.7.3
          workingDir: /config
          command: [kube-burner, init, -c, /config/config.yml, --uuid=${UUID}]
          volumeMounts:
            - {name: workdir, mountPath: /config}
      volumes:
        - name: config-src
          configMap:
            name: windows-fleet-config
        - name: workdir
          emptyDir: {}
JOBYAML
`

Security — DISA STIG-hardened job manifest

If your cluster enforces DISA STIG hardening (e.g. the restricted-v2 SCC, a compliance-operator profile, or an admission policy requiring non-root containers and no Linux capabilities), the Step 9 job manifest above may fail admission. Use this hardened variant instead — it adds a pod-level securityContext (non-root, RuntimeDefault seccomp profile) plus container-level securityContext (no privilege escalation, all capabilities dropped) on the init container and the kube-burner container:

`bash
cat << JOBYAML | oc apply -f -
apiVersion: batch/v1
kind: Job
metadata:
  name: kb-windows-fleet
  namespace: burner-windows-fleet
spec:
  backoffLimit: 0
  template:
    spec:
      serviceAccountName: kube-burner
      restartPolicy: Never
      securityContext:
        runAsNonRoot: true
        seccompProfile:
          type: RuntimeDefault
      initContainers:
        - name: copy-config
          image: quay.io/kube-burner/kube-burner:v2.7.3
          command: [sh, -c, "cp /config-src/* /config/"]
          securityContext:
            allowPrivilegeEscalation: false
            capabilities:
              drop: ["ALL"]
          volumeMounts:
            - {name: config-src, mountPath: /config-src}
            - {name: workdir,    mountPath: /config}
      containers:
        - name: kube-burner
          image: quay.io/kube-burner/kube-burner:v2.7.3
          workingDir: /config
          command: [kube-burner, init, -c, /config/config.yml, --uuid=${UUID}]
          securityContext:
            allowPrivilegeEscalation: false
            capabilities:
              drop: ["ALL"]
          volumeMounts:
            - {name: workdir, mountPath: /config}
      volumes:
        - name: config-src
          configMap:
            name: windows-fleet-config
        - name: workdir
          emptyDir: {}
JOBYAML
`

Step 11 — The customer demo narrative

Windows VMs have a distinctive boot progression in the OCP console. Use this script:

Phase 1 — DataVolume cloning (~1–3 minutes):
> "You can see the VMs are in 'Provisioning' — OpenShift is cloning the Windows golden image for each VM. This is like deploying VMs from a template in VMware. Each one gets its own private copy of the Windows disk."

Phase 2 — QEMU/BIOS startup (~1–2 minutes):
> "Now they're in 'Starting' — Windows is booting. BIOS POST, Windows kernel loading, services starting. Same as any Windows Server coming online."

Phase 3 — Windows Running:
> "There they go — Windows Server 2022, running on OpenShift. You can click any one of those and open the VNC console to see the Windows desktop. This is your workload, running on your cluster, without VMware."

Troubleshooting

| Problem | Fix |
|---|---|
| win2k22 DataVolume not found | Windows golden image not imported — complete Pre-flight section |
| VMs stuck in Provisioning > 10 min | CDI is still cloning the disk — check oc get datavolume -n burner-windows-fleet |
| cannot create resource "datavolumes" | Add cdi.kubevirt.io to ClusterRole (Step 3) |
| VMs stuck in Starting > 15 min | Windows boot stalled — check oc logs -n <ns> -l kubevirt.io=virt-launcher |
| serviceaccount "kube-burner" not found | Re-run Step 3 — create SA separately |
| OOMKilled virt-launcher pods | Worker node out of RAM — reduce VM_COUNT |
| Storage class not found | Set storageClassName in the DataVolumeTemplate to your cluster's default storage class |
