Test 21: OCP Web Burner — Production Web Application Density

Difficulty: ⭐⭐⭐⭐ Advanced
Time to run: ~20–30 minutes
What it does: Creates multi-container deployments with TLS Routes, HPAs, and NetworkPolicies — the closest thing to real production web app density
Requires: Multi-node OpenShift cluster, OpenShift Router

What is this test? 🌐

Imagine a shopping mall — not just one store, but hundreds of shops, each with its own front door (Route with TLS), security guard (NetworkPolicy), cash register system (sidecar container), and automatic resizing capability when there's a sale on (HorizontalPodAutoscaler).

web-burner is the test you run when a customer asks "can OpenShift handle my real web application at scale?" — because unlike the other density tests, this one creates workloads that look exactly like what runs in production.

Show this to a customer: "This isn't a synthetic benchmark. These are the same building blocks your apps use — Deployments, Routes, HPA, NetworkPolicies. We packed hundreds of them onto your cluster."

What each namespace contains

  • Multi-container Deployment (app + sidecar proxy)
  • Service with multiple ports
  • OpenShift Route with TLS edge termination
  • HorizontalPodAutoscaler targeting the Deployment
  • NetworkPolicy isolating the namespace
  • ConfigMap + Secret

Step-by-step guide

Step 1 — Verify pre-flight
oc whoami
oc get ingresscontroller -n openshift-ingress-operator
oc get apiservice v2.autoscaling
Step 2 — Create the project and RBAC
oc new-project burner-web-burner
oc create serviceaccount kube-burner -n burner-web-burner

Apply ClusterRole (must include route.openshift.io and autoscaling apiGroups) and ClusterRoleBinding.

Step 3 — Write config and templates
ITERATIONS=20
UUID="web-burner-$(date +%s)"
# Write config.yml and all 5 templates (deployment, service, route, hpa, networkpolicy)
# See full markdown guide for complete template content
Step 4 — Create ConfigMap
oc create configmap web-burner-config \
  --from-file=config.yml=/tmp/web-burner-config.yml \
  --from-file=deployment-template.yml=/tmp/web-deployment-template.yml \
  --from-file=service-template.yml=/tmp/web-service-template.yml \
  --from-file=route-template.yml=/tmp/web-route-template.yml \
  --from-file=hpa-template.yml=/tmp/web-hpa-template.yml \
  --from-file=networkpolicy-template.yml=/tmp/web-networkpolicy-template.yml \
  -n burner-web-burner
Step 5 — Launch the Job
cat << JOBYAML | oc apply -f -
# (Job YAML from full markdown guide)
JOBYAML

oc get pod -n burner-web-burner -w
oc logs -f job/kb-web-burner -n burner-web-burner
Step 6 — Watch the cluster

Tab 2: HPAs appearing — each watching a Deployment, ready to scale at 70% CPU.

Tab 3: TLS routes appearing and transitioning from unknown to Accepted.

What to say: "This namespace represents one production web application — it has a multi-container deployment with a sidecar, a TLS-terminated route, an autoscaler watching CPU, and network isolation from all other tenants."
Step 7 — Read results
INFO podLatency:
INFO   P50:  4.2s
INFO   P99:  14.3s
INFO Finished execution.
Step 8 — Clean up
oc delete job kb-web-burner -n burner-web-burner 2>/dev/null || true
for ns in $(oc get projects --no-headers -o custom-columns=NAME:.metadata.name | grep "^web-app-"); do
  oc delete project $ns
done
oc delete project burner-web-burner
oc delete clusterrole kube-burner 2>/dev/null || true
oc delete clusterrolebinding kube-burner 2>/dev/null || true
