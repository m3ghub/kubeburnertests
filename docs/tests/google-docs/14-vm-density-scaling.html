Test 14: VM Density Scaling — Finding Your Cluster's Ceiling

Difficulty: ⭐⭐⭐⭐ Expert
Time to run: 30–90 minutes (depends on how many VMs your cluster handles)
What it does: Progressively increases the number of running VMs in steps until the cluster reaches its limit — finding the exact maximum VM density
Requires: OpenShift Virtualization, at least 2 worker nodes
⚡ Pre-flight required: Before running this test, verify kube-burner is pullable on your cluster — see 00-preflight.


What is this test? 📈🖥️

This test answers the most important question for any virtualised infrastructure:

"How many VMs can this cluster actually handle before it falls over?"

Instead of guessing, this test climbs a controlled ladder — adding VMs in batches and waiting for all of them to reach Running before adding more. When VMs stop reaching Running within the timeout, or nodes show resource pressure — you have found the ceiling.



How the ladder works

VM Count over time:

    32 │                              ████
    16 │                    ████████████
     8 │          ████████████
     4 │  ████████
     2 │██
     0 └──────────────────────────────────► time
          run1   run2   run3   run4   run5

Each run: delete old VMs → create N new VMs → wait for all Running → record timing
If VMs stop reaching Running: STOP — you found the ceiling


What does it measure?

MetricWhat it means
vmiLatency P50/P95/P99Boot time percentiles at each VM count
Step completion timeHow long each batch takes to reach Running
First failure stepAt which VM count the cluster starts failing
Node resource pressureCPU/memory headroom at each step

Pre-flight checklist

  • Logged into the OpenShift web console
  • OpenShift Virtualization installed (oc get hyperconverged -A returns a result)
  • Cluster-admin permissions
  • Test 09 completed successfully (confirms VMs can boot on this cluster)
  • Check available RAM per worker node — each CirrOS VM needs 128Mi
oc get nodes -l node-role.kubernetes.io/worker \
  -o custom-columns='NAME:.metadata.name,RAM:.status.allocatable.memory'

Divide each node's RAM by 128Mi to estimate the per-node ceiling.
Example: 28Gi node ÷ 128Mi = ~224 VMs theoretical max (CPU and other limits will kick in first).

Click the >_ icon in the top-right of the console toolbar. Confirm it works:

Step 3 — Create the config files

The default VM template uses CirrOS — a tiny test OS that boots in seconds and uses ~128Mi RAM. See the OS options below if you want to use Windows or a different OS.

cat > /tmp/density-scale-config.yml << 'EOF'
global:
  gc: false
  measurements:
    - name: vmiLatency

jobs:
  - name: create-vms
    namespace: burner-density-scale
    jobType: create
    jobIterations: 1
    namespacedIterations: false
    qps: 10
    burst: 10
    waitWhenFinished: true
    maxWaitTimeout: 15m
    objects:
      - objectTemplate: vm-scale-template.yml
        replicas: 2

  - name: delete-vms
    namespace: burner-density-scale
    jobType: delete
    qps: 10
    burst: 10
    objects:
      - kind: VirtualMachine
        apiVersion: kubevirt.io/v1
        labelSelector:
          app: burner-scale
EOF

cat > /tmp/vm-scale-template.yml << 'EOF'
apiVersion: kubevirt.io/v1
kind: VirtualMachine
metadata:
  name: scale-vm-{{.Iteration}}-{{.Replica}}
  labels:
    app: burner-scale
spec:
  runStrategy: Always
  template:
    metadata:
      labels:
        app: burner-scale
    spec:
      domain:
        resources:
          requests:
            memory: 128Mi
        devices:
          disks:
            - name: containerdisk
              disk:
                bus: virtio
          interfaces:
            - name: default

        - name: default

EOF

Option 2 — Any OS from your cluster's golden images (recommended for Windows)

This template clones a golden image PVC instead of pulling from the internet. Works fully air-gapped. Ideal for Windows.

OSGolden PVC nameMemory per VMStorage per VM
Windows Server 2022win2k22-virtio8Gi60Gi
Windows Server 2019win2k19-virtio4Gi60Gi
Windows 11windows118Gi60Gi
RHEL 9rhel92Gi30Gi
Fedorafedora1Gi15Gi
⚠️ Storage warning: Cloning a 60Gi PVC per VM means 100 Windows VMs = 6TB of storage. Check available PV capacity first: oc get pv

Replace win2k22-virtio, memory, and storage for your chosen OS. Also set maxWaitTimeout: 30m or higher in the main config for Windows.

cat > /tmp/vm-scale-template.yml << 'EOF'
apiVersion: kubevirt.io/v1
kind: VirtualMachine
metadata:
  name: scale-vm-{{.Iteration}}-{{.Replica}}
  labels:
    app: burner-scale
spec:
  runStrategy: Always
  dataVolumeTemplates:
    - metadata:
        name: scale-vm-{{.Iteration}}-{{.Replica}}-disk
      spec:
        source:
          pvc:
            name: win2k22-virtio          # ← golden image PVC name
            namespace: openshift-virtualization-os-images
        storage:
          accessModes:
            - ReadWriteMany
          resources:
            requests:
              storage: 60Gi              # ← match the OS disk size
  template:
    metadata:
      labels:
        app: burner-scale
    spec:
      domain:
        resources:
          requests:
            memory: 8Gi                  # ← match the OS memory requirement
        devices:
          disks:
            - name: rootdisk
              disk:
                bus: virtio
          interfaces:
            - name: default
              masquerade: {}
      networks:
        - name: default
          pod: {}
      volumes:
        - name: rootdisk
          dataVolume:
            name: scale-vm-{{.Iteration}}-{{.Replica}}-disk
EOF
Step 3b — Verify both files exist
ls -lh /tmp/density-scale-config.yml \
        /tmp/vm-scale-template.yml

Both files must show non-zero sizes before continuing. If either is missing, re-run Step 3.

Note: spec.running: true is deprecated in KubeVirt v1.x. Templates above use runStrategy: Always. Both are functionally identical; running: true produces a harmless warning in kube-burner logs only.

VM Count | All Running? | P99 Boot Time | Notes
---------|--------------|---------------|------

5        | Yes          | ~19s          | Normal (live run: 19s VMIRunning P99)
10       | Yes          | ~25-40s       | Starting to see the cluster work

80       | Timeout?     | N/A           | Ceiling found
Live run results (this cluster, kube-burner v2.6.1, CirrOS): 2 VMs = 12s P99, 5 VMs = 19s P99. Faster than earlier estimates — kube-burner's image pre-load step ensures all nodes have the image cached before VMs start.

When a run times out (VMs never reach Running within 15 minutes) — that is your ceiling. The previous run's VM count is your reliable maximum.

Troubleshooting

ProblemFix
VMs stuck in SchedulingNot enough CPU or RAM — you found the ceiling. Record this count.
Job times out at maxWaitTimeout: 15mCeiling confirmed — note the count and stop here
image pull errorsCluster cannot reach quay.io — check pull secrets, or use golden image (Option 2)
Nodes show MemoryPressureHard ceiling hit — stop and record
virt-controller pod restartingYou have overloaded the control plane — hard ceiling
DataVolume clone stuck in PendingStorage class does not support ReadWriteMany — change to ReadWriteOnce or use a CSI driver that supports cloning


Auto-Escalation — Set It and Forget It

Instead of running one step at a time and manually increasing the count, you can set up a single config that runs all 8 rounds automatically (2 → 5 → 10 → 25 → 50 → 100 → 200 → 500 VMs). See the Markdown version for the full multi-round config and bash auto-stop script.

Force-stop a round that is stuck or failing

If a round is producing too many errors or VMs are failing to schedule and you don't want to wait for the full maxWaitTimeout, stop immediately:

# Stop kube-burner from waiting
oc delete job kb-escalation -n burner-escalation

# Delete VMs from the stuck round (change round-08 to whichever round is stuck)
oc delete vm -l kube-burner.io/job=round-08-create -n burner-escalation
# Watch them clear
oc get vm -n burner-escalation -w
What the failure count tells you: If a round creates N VMs but M fail to schedule, your ceiling is approximately N − M. The last fully clean round is your documented reliable maximum.
What you sawWhat it means
All VMs RunningCluster handled it — continue to the next round
Some VMs stuck in SchedulingCPU or RAM ceiling hit — stop here, record the last clean count
Many VMs in ImagePullBackOffImage pull issue, not a capacity ceiling — fix pull secrets first
virt-controller pod restartingControl plane overloaded — hard ceiling, stop immediately

After force-stopping, do not re-run earlier rounds. The ceiling has been found. Proceed straight to clean-up below.

Clean up after auto-escalation

When the run completes or stops early, clean up everything the auto-escalation section created:

oc delete job kb-escalation -n burner-escalation 2>/dev/null || true
oc delete configmap escalation-config -n burner-escalation 2>/dev/null || true
oc delete vm -l app=burner-escalation -n burner-escalation 2>/dev/null || true
oc delete project burner-escalation
oc delete clusterrolebinding kube-burner-virt-escalation
The kube-burner-virt ClusterRole is shared with the main test — do not delete it here. It is removed in Step 9 of the main guide.
