Test 24a — Windows VM Density Escalation (Set It and Forget It)

Category: OpenShift Virtualization — Windows Server 2022 VM Density
Namespace: burner-windows-density-escalation
Escalation: 2 → 5 → 10 → 20 → 40 VMs
Duration: ~90–180 min
Difficulty: ⭐⭐⭐⭐⭐ Expert

What this test does

Automatically runs 5 escalating rounds using Windows Server 2022 golden images cloned from the win2k22 PVC in openshift-virtualization-os-images. Each round provisions VMs (including full PVC clones), waits for all VMs to reach Running state, then deletes everything before the next round.

Time warning: Each Windows VM requires a 60Gi PVC clone. At Round 5 (40 VMs) that is 2.4 Ti of PVC cloning. Allow 120 min per round on standard storage.

Prerequisites

  • OpenShift cluster with OpenShift Virtualization installed
  • oc CLI logged in with cluster-admin
  • Verify the Windows PVC is available:
    • oc get pvc win2k22 -n openshift-virtualization-os-images

    Expected:

    NAME      STATUS   VOLUME      CAPACITY   ACCESS MODES   STORAGECLASS
win2k22   Bound    pvc-xxxxx   60Gi       RWX            ocs-storagecluster-ceph-rbd
  • If the PVC name differs on your cluster, update name: win2k22 in the VM template.
  • Each VM needs 8 Gi RAM and 2 vCPUs — check available capacity: oc describe nodes | grep -A5 "Allocatable"

    Step 4 — Launch the job

    cat <<'EOF' | oc apply -f -
apiVersion: batch/v1
kind: Job
metadata:
  name: kb-win-escalation
  namespace: burner-windows-density-escalation
spec:
  template:
    spec:
      serviceAccountName: kube-burner
      initContainers:
        - name: copy-config
          image: busybox
          command: ["sh","-c","cp /configmap/* /config/"]
          volumeMounts:
            - name: configmap-vol
              mountPath: /configmap
            - name: config-vol
              mountPath: /config
      containers:
        - name: kube-burner
          image: quay.io/kube-burner/kube-burner:v2.7.3
          command:
            - kube-burner
            - init
            - -c
            - /config/config.yml
            - --uuid
            - win-escalation-001
          volumeMounts:
            - name: config-vol
              mountPath: /config
      volumes:
        - name: configmap-vol
          configMap:
            name: windows-escalation-config
        - name: config-vol
          emptyDir: {}
      restartPolicy: Never
EOF
    Re-run note: Change --uuid win-escalation-001 to a unique value on each run.

    Security — DISA STIG-hardened job manifest

    If your cluster enforces DISA STIG hardening (e.g. the restricted-v2 SCC, a compliance-operator profile, or an admission policy requiring non-root containers and no Linux capabilities), the Step 4 job manifest above may fail admission. Use this hardened variant instead — it adds a pod-level securityContext (non-root, RuntimeDefault seccomp profile) plus container-level securityContext (no privilege escalation, all capabilities dropped) on both the init container and the kube-burner container:

    cat <<'EOF' | oc apply -f -
apiVersion: batch/v1
kind: Job
metadata:
  name: kb-win-escalation
  namespace: burner-windows-density-escalation
spec:
  template:
    spec:
      serviceAccountName: kube-burner
      securityContext:
        runAsNonRoot: true
        seccompProfile:
          type: RuntimeDefault
      initContainers:
        - name: copy-config
          image: registry.redhat.io/ubi9/ubi-minimal:latest
          command: ["sh","-c","cp /configmap/* /config/"]
          securityContext:
            allowPrivilegeEscalation: false
            capabilities:
              drop: ["ALL"]
          volumeMounts:
            - name: configmap-vol
              mountPath: /configmap
            - name: config-vol
              mountPath: /config
      containers:
        - name: kube-burner
          image: quay.io/kube-burner/kube-burner:v2.7.3
          command:
            - kube-burner
            - init
            - -c
            - /config/config.yml
            - --uuid
            - win-escalation-001
          securityContext:
            allowPrivilegeEscalation: false
            capabilities:
              drop: ["ALL"]
          volumeMounts:
            - name: config-vol
              mountPath: /config
      volumes:
        - name: configmap-vol
          configMap:
            name: windows-escalation-config
        - name: config-vol
          emptyDir: {}
      restartPolicy: Never
EOF
    Note: The init container image was swapped from busybox to registry.redhat.io/ubi9/ubi-minimal:latest since STIG-locked registries typically only permit signed Red Hat UBI images.

    Step 5 — Monitor

    Watch job pod
    
oc get pods -n burner-windows-density-escalation -w


    Stream logs
    
oc logs -f job/kb-win-escalation -n burner-windows-density-escalation


    Watch DataVolume cloning (the slow part for Windows)
    
watch -n15 'oc get dv -n burner-windows-density-escalation | grep -v Succeeded | head -20'


    Watch VM status
    
watch -n15 'oc get vm -n burner-windows-density-escalation | tail -20'

    Force-stop a stuck or failing round

    oc delete job kb-win-escalation -n burner-windows-density-escalation


    oc delete vm -l app=windows-density-escalation -n burner-windows-density-escalation --wait=false
    


    oc delete dv --all -n burner-windows-density-escalation --wait=false
    


    oc get vm,dv -n burner-windows-density-escalation -w

    Cleanup

    oc delete job kb-win-escalation -n burner-windows-density-escalation 2>/dev/null || true
oc delete configmap windows-escalation-config -n burner-windows-density-escalation 2>/dev/null || true
oc delete vm -l app=windows-density-escalation -n burner-windows-density-escalation --wait=false 2>/dev/null || true
oc delete dv --all -n burner-windows-density-escalation --wait=false 2>/dev/null || true
oc delete project burner-windows-density-escalation
oc delete clusterrole kube-burner-virt
oc delete clusterrolebinding kube-burner-virt-win-escalation
