Test 09c: RHEL 9 Density Escalation — Set It and Forget It

Difficulty: ⭐⭐⭐⭐ Advanced
Time to run: 2–4 hours (4 rounds unattended)
What it does: Automatically escalates through 4 rounds of increasing RHEL 9 VM density — find your cluster's real-OS VM ceiling
Requires: OpenShift Virtualization 4.x, rhel9 DataSource Ready: True, storage class with sufficient capacity
Companion test: Run Test 09b first to confirm 3 RHEL VMs boot successfully, then use this to find your ceiling.
⚡ Pre-flight required: See 00-preflight.md — Checks 1–6 all apply.
STIG / quota-enforced clusters: Use the quota-safe Job variant in Step 8. See CONCERN-013.

!Diagram

What this test does

Runs 4 sequential rounds of increasing RHEL 9 VM density. Each round creates VMs, waits for all to reach Running, records latency, deletes them and their PVCs, then moves automatically to the next round.

Round 1:  3 RHEL VMs  →  all Running  →  delete  →  next
Round 2:  6 RHEL VMs  →  all Running  →  delete  →  next
Round 3: 10 RHEL VMs  →  all Running  →  delete  →  next
Round 4: 15 RHEL VMs  →  all Running  →  delete  →  done

If a round exceeds its timeout, kube-burner stops and reports the last successful round. That is your cluster's RHEL VM ceiling.

Round summary

RoundVMsRAM neededStorage neededTimeoutTypical time ------------------ 13~6 Gi~90 Gi25m~8 min 26~12 Gi~180 Gi35m~15 min 310~20 Gi~300 Gi50m~25 min 415~30 Gi~450 Gi75m~40 min
Storage is the primary constraint here. Unlike CirrOS (Test 09a) which uses no storage, each RHEL VM clones a 30Gi PVC. 15 VMs = 450Gi of storage required for Round 4. Check your storage class capacity before running.

Before you start

Confirm RHEL golden image is ready

oc get datasource rhel9 -n openshift-virtualization-os-images \
  -o jsonpath='{.status.conditions[?(@.type=="Ready")].status}'

Expected: True



Check available worker node RAM (need ~30Gi free for Round 4)

oc adm top nodes -l node-role.kubernetes.io/worker


Check available storage (need ~450Gi free for Round 4)

oc get storageclass

Security — DISA STIG-hardened job manifest

If your cluster enforces DISA STIG hardening (e.g. the restricted-v2 SCC, a compliance-operator profile, or an admission policy requiring non-root containers and no Linux capabilities), the standard job manifest above may fail admission. Use this hardened variant instead — it adds a pod-level securityContext (non-root, RuntimeDefault seccomp profile) plus container-level securityContext (no privilege escalation, all capabilities dropped) on every container in the Job.

cat <<'EOF' | oc apply -f -
apiVersion: batch/v1
kind: Job
metadata:
  name: kb-rhel-escalation
  namespace: burner-rhel-escalation
spec:
  backoffLimit: 0
  template:
    spec:
      serviceAccountName: kube-burner
      restartPolicy: Never
      securityContext:
        runAsNonRoot: true
        seccompProfile:
          type: RuntimeDefault
      initContainers:
        - name: copy-config
          image: quay.io/kube-burner/kube-burner:v2.6.1
          command: [sh, -c, "cp /config-src/* /config/"]
          securityContext:
            allowPrivilegeEscalation: false
            capabilities:
              drop: ["ALL"]
          volumeMounts:
            - {name: config-src, mountPath: /config-src}
            - {name: workdir,    mountPath: /config}
      containers:
        - name: kube-burner
          image: quay.io/kube-burner/kube-burner:v2.6.1
          workingDir: /config
          command: [kube-burner, init, -c, /config/config.yml, --uuid=rhel-escalation-001]
          securityContext:
            allowPrivilegeEscalation: false
            capabilities:
              drop: ["ALL"]
          volumeMounts:
            - {name: workdir, mountPath: /config}
      volumes:
        - name: config-src
          configMap:
            name: rhel-escalation-config
        - name: workdir
          emptyDir: {}
EOF

Step 7 — Read the results

At the end of each round, kube-burner logs the VMIRunning latency. A successful 4-round run looks like:

level=info msg="rhel-round1-create: VMIRunning 99th: 145000 ms  max: 162000 ms  avg: 138000 ms"
level=info msg="rhel-round2-create: VMIRunning 99th: 167000 ms  max: 198000 ms  avg: 155000 ms"
level=info msg="rhel-round3-create: VMIRunning 99th: 210000 ms  max: 245000 ms  avg: 195000 ms"
level=info msg="rhel-round4-create: VMIRunning 99th: 278000 ms  max: 310000 ms  avg: 260000 ms"

Interpretation: If P99 stays below 300 seconds through Round 4, your cluster handles 15 simultaneous RHEL VMs well. If a round times out — that round minus 1 is your sustainable ceiling.
