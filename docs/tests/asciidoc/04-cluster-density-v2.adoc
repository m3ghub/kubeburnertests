= Test 04: Cluster Density v2 — The Mega City Test

[sidebar]
****
_Difficulty:_ ⭐⭐ Intermediate  
_Time to run:_ ~20 minutes  
_What it does:_ An enhanced version of Cluster Density that creates richer application stacks including NetworkPolicies and multiple container workloads — closer to what real enterprise clusters run
****

TIP: _⚡ Pre-flight required:_ Before running this test, verify kube-burner is pullable on your cluster and your environment is ready — see _link:00-preflight.md[00-preflight.md]_.

'''

== What is this test? 🏗️

Think of Cluster Density (Test 03) as building a small town.  
_Cluster Density v2_ builds a _mega city_ — same idea, but with:
- More objects per namespace
- `NetworkPolicy` rules (like security fences between neighbourhoods)
- Multiple workload types per iteration
- Higher pressure on the cluster's control plane

If your cluster can handle this test well, it is ready for real enterprise workloads.

'''

== How v2 differs from v1

[cols="1,1,1", options="header"]
|===
| Feature | Cluster Density (v1) | Cluster Density v2

| Objects per namespace | Deployment + Service + ConfigMap + Secret | All of v1 _plus_ NetworkPolicy + extra Deployments
| Workloads | 1 Deployment | 3+ Deployments with different sizes
| Network pressure | Minimal | Medium (NetworkPolicies are enforced by CNI)
| Control plane load | Medium | High
| Realistic? | Yes | More realistic
|===

'''

== How it works

----
Each namespace (iteration) gets:

  Namespace: burner-cdv2-0
  ┌──────────────────────────────────────────────────────────────────┐
  │  Deployment-A (1 replica)  ──► Pod 🟢                           │
  │  Deployment-B (1 replica)  ──► Pod 🟢   (second workload)       │
  │  Service-A                 ──► routes to Deployment-A           │
  │  Service-B                 ──► routes to Deployment-B           │
  │  ConfigMap (x2)            ──► app configuration                │
  │  Secret                    ──► credentials                      │
  │  NetworkPolicy             ──► only allow traffic from app label│
  └──────────────────────────────────────────────────────────────────┘

  × N iterations = N fully isolated neighbourhoods with security rules
----

'''

* [ ] kube-burner installed

== Step-by-step guide

=== Step 1 — Create the namespace

NOTE: _Do this first — every other step depends on it._

[source,bash]
----
oc new-project burner-cdv2
----

You should see:
----
Now using project "burner-cdv2" on server "https://api.<your-cluster>:6443"
----

NOTE: _OpenShift only:_ Never use `kube-` at the start of the name — it is reserved by the system and will be rejected.

=== Step 2 — Set up RBAC

Every test needs a `ServiceAccount`, `ClusterRole`, and `ClusterRoleBinding`. Run all three commands — they are safe to re-run if any already exist.

_2a — Create the ServiceAccount in this namespace:_

[source,bash]
----
oc create serviceaccount kube-burner -n burner-cdv2 \
  --dry-run=client -o yaml | oc apply -f -
----

_2b — Apply the ClusterRole and ClusterRoleBinding (once per cluster):_

NOTE: These are applied inline below — no local file needed. Safe to re-run at any time.

[source,bash]
----
oc apply -f - <<'EOF'
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata:
  name: kube-burner
rules:
  - apiGroups: [""]
    resources: [namespaces, pods, services, endpoints, configmaps, secrets, nodes, events, replicationcontrollers, serviceaccounts]
    verbs: [get, list, watch, create, delete, update, patch]
  - apiGroups: [apps]
    resources: [deployments, replicasets, statefulsets, daemonsets]
    verbs: [get, list, watch, create, delete, update, patch]
  - apiGroups: [batch]
    resources: [jobs]
    verbs: [get, list, watch, create, delete, update, patch]
  - apiGroups: [networking.k8s.io]
    resources: [networkpolicies, ingresses]
    verbs: [get, list, watch, create, delete, update, patch]
  - apiGroups: [kubevirt.io]
    resources: [virtualmachines, virtualmachineinstances]
    verbs: [get, list, watch, create, delete, update, patch]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRoleBinding
metadata:
  name: kube-burner
roleRef:
  apiGroup: rbac.authorization.k8s.io
  kind: ClusterRole
  name: kube-burner
subjects:
  - kind: ServiceAccount
    name: kube-burner
    namespace: burner-cdv2
EOF
----

_2c — Add this namespace to the ClusterRoleBinding:_

[source,bash]
----
oc patch clusterrolebinding kube-burner \
  --type=json \
  -p='[{"op":"add","path":"/subjects/-","value":{"kind":"ServiceAccount","name":"kube-burner","namespace":"burner-cdv2"}}]' 2>/dev/null || true
----

NOTE: The `|| true` at the end means this command will not fail if the namespace is already listed. It is safe to run every time.

_Verify all three are in place before continuing:_

[source,bash]
----
oc get serviceaccount kube-burner -n burner-cdv2
oc get clusterrole kube-burner
oc get clusterrolebinding kube-burner -o jsonpath='{.subjects[*].namespace}'
----

The last command should include `burner-cdv2` in the output.

=== Step 3 — Create config files

Create `cdv2-config.yml`:

[source,bash]
----
cat > /tmp/cdv2-config.yml << 'EOF'
global:
  gc: true
  measurements:
    - name: podLatency

jobs:
  - name: cluster-density-v2
    namespace: burner-cdv2
    jobType: create
    jobIterations: 5
    namespacedIterations: true
    qps: 20
    burst: 20
    objects:
      - objectTemplate: deployment-a.yml
        replicas: 1
      - objectTemplate: deployment-b.yml
        replicas: 1
      - objectTemplate: service-a.yml
        replicas: 1
      - objectTemplate: service-b.yml
        replicas: 1
      - objectTemplate: configmap.yml
        replicas: 2
      - objectTemplate: secret.yml
        replicas: 1
      - objectTemplate: netpol.yml
        replicas: 1
    waitWhenFinished: true
    podWait: true
    maxWaitTimeout: 15m
EOF
----

Create `deployment-a.yml`:

[source,bash]
----
cat > /tmp/deployment-a.yml << 'EOF'
apiVersion: apps/v1
kind: Deployment
metadata:
  name: burner-app-a-{{.Iteration}}
  labels:
    app: burner-a-{{.Iteration}}
    tier: frontend
spec:
  replicas: 1
  selector:
    matchLabels:
      app: burner-a-{{.Iteration}}
  template:
    metadata:
      labels:
        app: burner-a-{{.Iteration}}
        tier: frontend
    spec:
      containers:
        - name: frontend
          image: registry.k8s.io/pause:3.9
          resources:
            requests:
              cpu: 1m
              memory: 10Mi
EOF
----

Create `deployment-b.yml`:

[source,bash]
----
cat > /tmp/deployment-b.yml << 'EOF'
apiVersion: apps/v1
kind: Deployment
metadata:
  name: burner-app-b-{{.Iteration}}
  labels:
    app: burner-b-{{.Iteration}}
    tier: backend
spec:
  replicas: 1
  selector:
    matchLabels:
      app: burner-b-{{.Iteration}}
  template:
    metadata:
      labels:
        app: burner-b-{{.Iteration}}
        tier: backend
    spec:
      containers:

Create `service-a.yml`:

----

  name: burner-svc-a-{{.Iteration}}

    app: burner-a-{{.Iteration}}

    - port: 80

----

Create `service-b.yml`:

[source,bash]
----
cat > /tmp/service-b.yml << 'EOF'

kind: Service

  name: burner-svc-b-{{.Iteration}}

  selector:
    app: burner-b-{{.Iteration}}
  ports:
    - port: 8080
EOF
----

Create `configmap.yml`:

[source,bash]
----
cat > /tmp/configmap.yml << 'EOF'
apiVersion: v1
kind: ConfigMap
metadata:
  name: burner-config-{{.Iteration}}-{{.Replica}}
data:
  tier: "{{.Iteration}}"
  replica: "{{.Replica}}"
EOF
----

Create `secret.yml`:

[source,bash]
----
cat > /tmp/secret.yml << 'EOF'
apiVersion: v1
kind: Secret
metadata:
  name: burner-secret-{{.Iteration}}
type: Opaque

  api-key: dGVzdC1rZXk=
EOF
----

Create `netpol.yml` (the NetworkPolicy — the security fence):

[source,bash]
----
cat > /tmp/netpol.yml << 'EOF'
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: burner-netpol-{{.Iteration}}
spec:
  podSelector:
    matchLabels:
      app: burner-a-{{.Iteration}}
  policyTypes:
    - Ingress
  ingress:
    - from:
        - podSelector:
            matchLabels:
              tier: frontend
EOF
----

=== Step 4 — Package into a ConfigMap

[source,bash]
----
oc create configmap cdv2-config \
  --from-file=config.yml=/tmp/cdv2-config.yml \
  --from-file=deployment-a.yml=/tmp/deployment-a.yml \
  --from-file=deployment-b.yml=/tmp/deployment-b.yml \
  --from-file=service-a.yml=/tmp/service-a.yml \
  --from-file=service-b.yml=/tmp/service-b.yml \
  --from-file=configmap.yml=/tmp/configmap.yml \
  --from-file=secret.yml=/tmp/secret.yml \
  --from-file=netpol.yml=/tmp/netpol.yml \
  -n burner-cdv2
----

'''

=== Step 5 — Run the test!

[source,bash]
----
cat <<'EOF' | oc apply -f -
apiVersion: batch/v1
kind: Job
metadata:
  name: kb-cdv2
  namespace: burner-cdv2
spec:
  backoffLimit: 0
  template:
    spec:
      serviceAccountName: kube-burner
      restartPolicy: Never
      initContainers:
        - name: copy-config
          image: quay.io/kube-burner/kube-burner:v2.7.3
          command: [sh, -c, "cp /config-src/* /config/"]
          volumeMounts:
            - {name: config-src, mountPath: /config-src}
            - {name: workdir,    mountPath: /config}
      containers:
        - name: kube-burner
          image: quay.io/kube-burner/kube-burner:v2.7.3
          workingDir: /config
          command: [kube-burner, init, -c, /config/config.yml, --uuid=cdv2-001]
          volumeMounts:
            - {name: workdir, mountPath: /config}
      volumes:
        - name: config-src
          configMap:
            name: cdv2-config
        - name: workdir
          emptyDir: {}
EOF
----

=== Security — DISA STIG-hardened job manifest

If your cluster enforces DISA STIG hardening (e.g. the `restricted-v2` SCC, a compliance-operator profile, or an admission policy requiring non-root containers and no Linux capabilities), the Step 5 job manifest above may fail admission. Use this hardened variant instead — it adds a pod-level `securityContext` (non-root, `RuntimeDefault` seccomp profile) plus container-level `securityContext` (no privilege escalation, all capabilities dropped) on both the init container and the `kube-burner` container:

[source,bash]
----
cat <<'EOF' | oc apply -f -
apiVersion: batch/v1
kind: Job
metadata:
  name: kb-cdv2
  namespace: burner-cdv2
spec:
  backoffLimit: 0
  template:
    spec:
      serviceAccountName: kube-burner
      securityContext:
        runAsNonRoot: true
        seccompProfile:
          type: RuntimeDefault
      restartPolicy: Never
      initContainers:
        - name: copy-config
          image: quay.io/kube-burner/kube-burner:v2.7.3
          command: [sh, -c, "cp /config-src/* /config/"]
          securityContext:
            allowPrivilegeEscalation: false
            capabilities:
              drop: ["ALL"]
          volumeMounts:
            - {name: config-src, mountPath: /config-src}
            - {name: workdir,    mountPath: /config}
      containers:
        - name: kube-burner
          image: quay.io/kube-burner/kube-burner:v2.7.3
          workingDir: /config
          command: [kube-burner, init, -c, /config/config.yml, --uuid=cdv2-001]
          securityContext:
            allowPrivilegeEscalation: false
            capabilities:
              drop: ["ALL"]
          volumeMounts:
            - {name: workdir, mountPath: /config}
      volumes:
        - name: config-src
          configMap:
            name: cdv2-config
        - name: workdir
          emptyDir: {}
EOF
----

'''

== Troubleshooting

[cols="1,1", options="header"]
|===
| Problem | Fix

| `networkpolicies is forbidden` | Add `networking.k8s.io` to ClusterRole rules
| NetworkPolicy creation slow | CNI is busy processing rules — reduce iterations
| Pods from different deployments cannot communicate | This is expected! NetworkPolicy is working correctly
|===
